# 00 项目概述（ACM-Trainer）

## 1. 项目名称
**ACM-Trainer（ACM 训练助手）** —— 面向个人 ACM/ICPC 学习与训练的本地桌面应用。

## 2. 项目背景与目标
- 用户为计算机专业大二学生，正在进行 ACM/ICPC 竞赛的学习与训练。
- 痛点：题库分散、练习记录难以统计、错题与题解笔记零散、缺少针对性的水平反馈。
- 目标：提供一个**本机自用、单人使用**的一站式训练管理工具，覆盖：
  - 刷题（**三大题库**：Codeforces、洛谷 P 题、力扣 LeetCode 算法题，合计 3 万余题）
  - 练习记录、统计与**难度分布分析**
  - **技能树与学习路径**（54 个知识点，7 层；**5 个国内比赛赛道**：蓝桥杯 / 天梯赛 / ICPC·CCPC / NOIP·CSP-S / 牛客多校）
  - **题单**（题库勾选 / 粘贴题号识别 / 按知识点+难度生成）与**训练计划**（日历排期、没空日顺延、打卡）
  - **题单内间隔复习**（1/3/7/14/30/60 天阶梯 + 今日复习反馈）
  - **首页推荐习题**（已练习按遗忘曲线排序 / 未练习优先「练习中」知识点）与**已练习标签**展示
  - 错题本与题解笔记
  - 算法代码模板库
  - 虚拟比赛/限时训练
  - 参赛水平评估（折算近似 CF Rating + 称号；洛谷/力扣练习水平独立展示）

## 3. 开发方式
采用 **SDD（Specification-Driven Development，规格驱动开发）**：
1. 先产出并确认规范文档（本文档体系）；
2. 依据文档中的任务分解（05）按依赖关系逐步实现；
3. 每完成一个里程碑进行验证与验收。

## 6. 运行环境约束
- 系统：Windows 10/11（目标平台）；应用为本地桌面应用。
- 网络：首次同步 Codeforces / 洛谷 / 力扣题库及查看题面**需要联网**；已同步的数据支持**离线浏览**。
- 单用户、无账号体系、数据全部保存在本机 SQLite。

## 7. 项目范围（v1.0）
### 范围内
- 题库浏览/筛选/同步（CF 数据源；v1.1 起增加洛谷、v1.9 起增加力扣）、练习记录、统计图表、错题本、Markdown 笔记、
  代码模板库、虚拟比赛、水平评估、本地设置。当前交付版本能力见 §9。

### 范围外（v1.0 不做）
- 账号系统、云同步、多用户排行榜；
- 站内代码评测（提交在 CF 页面进行，应用内手动记录结果）；
- 爬取洛谷等其他 OJ 数据（**v1.1 洛谷与 v1.9 力扣为后续版本追加，已实现**）；
- 手机端 / 多平台发布。

## 8.9 当前版本功能补充（v1.17.0：标签筛选取并集 + 按命中标签数排序）
> v1.17.0 是**行为变更版本**（不是新功能页）：**无新增数据表、无新增 IPC 通道、无新增设置项**，改动只有 1 处 SQL 语义（`ProblemFilter.tags`）+ `buildOrderSql()` 增加一个排序前缀 + 前端 2 个展示元素。
> 细节见 docs/01 FR-37 与「FR-37 实施契约补充（v1.17）」、docs/03 §28、docs/08 §23。

**用户需求原文**：「将标签筛选从取交集改为取并集，按照满足的标签数排列」。

**能力变更：标签从「必须同时带全部已选标签」变成「命中任意一个即入选，命中越多越靠前」。**

| 场景 | v1.16.0（改前：交集） | v1.17.0（改后：并集） |
| ---- | ---- | ---- |
| 点技能树「贪心」知识点（该节点挂 `greedy` + `贪心` 两个标签，点节点 = 勾选两个标签） | 要求题目**同时带**两个标签，而多数题只带其中之一 → 经常筛出 **0 题** | **命中任一**标签即入选，能列出该知识点的全部相关题 |
| 手动勾选 `dp` + `graphs` 两个标签 | 只返回同时带两标签的题（SQL：`GROUP BY pt.problem_id HAVING COUNT(DISTINCT t.id) = 2`） | 返回带任一标签的题，其中**命中两个的排最前** |
| 列表排序 | 只有用户所选排序（按难度 / 按题号 / 按 AC 数） | 已选标签数 > 1 时先按**命中标签数降序**，命中数相同再按用户所选排序（难度 / 题号 / AC 数等） |
| 每题命中几个标签可见吗 | 不可见，只能逐题看标签自己数 | 题目行标签区末尾显示角标 `命中 N/M`（琥珀色，`title` 为「命中 N / M 个已选标签」）；「已选」条提示「取并集 · 命中标签越多越靠前」 |
| 只选 1 个标签 / 不选标签 | 交集与并集等价 | 行为不变：**SQL 与旧版逐字符一致**，不显示角标与提示（无排序意义） |
| 题单「按知识点自动抽题」（`filter.tagsAny`） | 本来就是并集 | **未改动**，不受本次变更影响 |

**为什么要改（动机）**：技能树的知识点节点会挂**多个标签**（例如「贪心」节点同时挂 `greedy` 与 `贪心`），点节点等于勾选它关联的**全部**标签；交集语义却要求题目同时带全部标签，于是「点知识点 → 一题都没有」成了常见现象，与「点节点就是想看这个知识点的题」的预期相反。改成并集后，点节点能列出该知识点的全部相关题，再用「命中标签数降序」把最对口（同时命中多个相关标签）的题顶到前面。

| 能力 | 说明 |
| ---- | ---- |
| **SQL 语义（后端）** | `src/main/db/repositories/problems.ts` 的 `buildWhere()` 中 `filter.tags` 分支弃用 `GROUP BY pt.problem_id HAVING COUNT(DISTINCT t.id) = <已选标签数>`，改为子查询并集：`p.id IN (SELECT pt.problem_id FROM problem_tags pt JOIN tags t ON t.id = pt.tag_id WHERE t.name IN (@tag0, …))`（未知标签依旧被忽略） |
| **排序前缀（后端）** | 新增私有函数 `matchedTagsOrderPrefix(tags?: string[]): string`：未选标签返回**空串**（此时 ORDER BY 与旧版逐字符一致）；有标签时返回 `(SELECT COUNT(DISTINCT t.id) FROM problem_tags pt JOIN tags t ON t.id = pt.tag_id WHERE pt.problem_id = p.id AND t.name IN (@tag0, @tag1)) DESC, `，由 `buildOrderSql(filter)` 拼到 **4 个 return 分支**的 ORDER BY 最前面 |
| **绑定参数共享约束（易踩坑）** | 排序子查询复用的 `@tagN` 绑定参数由 `buildWhere()` 注册，因此调用方**必须先调用 `buildWhere()`、再执行 ORDER BY**（`list()` 与 `candidates()` 都是这个顺序）；两者不能拆开单独使用，否则 SQL 执行时缺参数 |
| **命中数可见化（前端）** | `src/renderer/src/pages/ProblemsPage.vue` 新增 `matchCount(row: ProblemRow): number`（用 `row.tags` 与已选标签集合求交，**不在 SQL 里回传**命中数）；已选标签数 > 1 且该题命中数 > 0 时显示 `命中 N/M` 角标（class `.mini-tag.match`，琥珀色）；「已选」条在「全部清空」后新增 `取并集 · 命中标签越多越靠前`（`.match-hint`） |
| **验收数字（v1.17.0 实跑）** | 单元/集成/渲染测试 **487/487（44 文件）**（v1.16.0：474/474（43 文件），新增 **13 例**：`tests/integration/problems-tag-union.test.ts` 10 例 + `tests/renderer/problems-knowledge-filter.test.ts` 3 例）、verify:gui **110/110**（v1.16.0：105/105，新增 5 项）、verify:smoke **33/33**（回归未破）、`tsc --noEmit -p tsconfig.node.json` 与 `vue-tsc --noEmit -p tsconfig.web.json` 均 **0 错误**；新增截图 `docs/images/04b-tags-union.png`（题库页同时选中 `dp` + `graphs` 后的列表，含并集提示与命中数角标） |
| **回退方式** | 把 `buildWhere()` 的 `filter.tags` 分支与 `matchedTagsOrderPrefix()` 涉及的两处 SQL 还原即可；标签交集语义**不涉及任何数据迁移**（`problem_tags` 表结构未变） |

## 8.10 当前版本功能补充（v1.18.0：中英文标签映射）
> v1.18.0 是**数据归一版本**：**无新增数据表、无新增 IPC 通道、无新增设置项、无新字段**，改动是 1 个新共享模块 + 1 个迁移函数 + 写入/查询/统计三侧的归一调用。
> 细节见 docs/01 FR-38 与「FR-38 实施契约补充（v1.18）」、docs/03 §29、docs/08 §24。

**问题：同一个概念在题库里是两套标签。** CF 题带英文标签（`greedy` / `dp` / `graphs`），洛谷与力扣题带中文标签（`贪心` / `动态规划` / `图论`）；而技能树节点的标签本来就是中英混排的（「并查集」节点 `tags: ['dsu', '并查集']`）。`tags` 表以标签名为唯一键 → 两种拼写就是两行 → 同一概念劈成两半。真实库实测：`dsu + 并查集` **交集 0 → 并集 907**，`greedy + 贪心` **交集 0 → 并集 5752**（交集为 0 说明不是「少数题同时带两者」，而是两批题完全不重叠）。后果有三：按英文筛与按中文筛得到不相交的两批题；点知识点时同一道题被算作「命中 2 个不同标签」，v1.17 的命中数排序与 `命中 N/M` 角标虚高；首页「已练习标签」里同一概念两个 chip 各带一半题数。

**方案：canonical 取中文 + 写入即物化。** 新增 `src/shared/tag-map.ts`（126 行，`TAG_ALIASES` 共 **53 canonical + 71 别名 = 124 名称**、`canonicalTag()`、`canonicalTags()`、`TAG_ALIAS_TOTAL`）；`upsertMany()` 写标签时走 `canonicalTags(p.tags)`，一次改动覆盖 CF / 洛谷 / 力扣三条写入路径。选中文的理由：UI 全中文，且中文标签覆盖面大得多（洛谷 452 + 力扣 171 vs CF 122）。**物化而不是查询期展开**的理由：命中数排序是 `COUNT(DISTINCT t.id)`（按标签行计数）、`tagUsage` 是 `GROUP BY t.id`（按行分组）—— 一个概念只有一行时两者天然正确，查询期展开会把同一概念算成 2 个命中，排序与角标一起错。

| 能力 | 说明 |
| ---- | ---- |
| **写入侧（1 处）** | `src/main/db/repositories/problems.ts` 的 `upsertMany()`：`for (const tagName of canonicalTags(p.tags))` —— 一题同时带 `greedy` 与 `贪心` 时去重，只留 `贪心` 一行 |
| **查询侧（4 处）** | `buildWhere()` 的 `filter.tags`（`@tagN`）与 `filter.tagsAny`（`@anyTagN`）、`matchedTagsOrderPrefix()`（命中数排序前缀）、`idsForKnowledge()`（位置参数 `?`），外加 `tagUsage()` 的标签过滤，全部先 `canonicalTags()` 再拼参数 —— 否则库里是中文、查询拼英文会**静默零结果** |
