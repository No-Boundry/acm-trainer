# 01 需求规格说明书（SRS）—— ACM-Trainer

- 版本：v1.0（基线）；v1.1–v1.10 的需求以**追加章节**方式记录（FR-8/FR-6.6/FR-9/FR-10/FR-11/FR-17/FR-18，v1.9 的 FR-21 ~ FR-23，v1.9.1 的 FR-24 ~ FR-25，以及 **v1.10 的 FR-26 ~ FR-29**：技能树扩展与国内比赛赛道 / 题单 / 训练计划 / 题单内间隔复习）
- 状态：待评审
- 说明：本说明书定义 ACM-Trainer v1.0 的全部功能与非功能需求，是开发、测试与验收的契约依据；追加章节为后续版本的实际交付需求。

## 1. 引言

### 1.1 目的
为 ACM-Trainer 桌面应用定义明确、可验证的需求规格，作为概要设计（02）、详细设计（03）、测试（04）与任务分解（05）的输入。

### 1.2 读者
项目开发者（本人）、评审者。

### 1.3 术语
| 术语 | 含义 |
| ---- | ---- |
| CF | Codeforces（Codeforces.com） |
| CF Rating | Codeforces 积分体系中的选手分值 |
| 力扣 / LC | 力扣中文站（leetcode.cn）；本文档中 `LC` 亦指该题源与其题目 id 前缀（如 `LC1`） |
| AC | Accepted，通过 |
| WA / TLE / RE / MLE / CE | 错误答案 / 超时 / 运行时错误 / 超内存 / 编译错误 |
| 罚时（Penalty） | ACM 比赛规则中错误提交的惩罚时间，每题 20 分钟 |
| 知识点（Tag） | 题目的算法标签，如 dp、graph、math |
| 题面 | 题目描述正文（Codeforces 网页提供，API 不含） |

## 2. 总体描述

### 2.1 产品定位
面向个人 ACM 训练的一站式本地桌面工具：**题库 → 练习 → 记录 → 复盘（错题/笔记）→ 模板沉淀 → 虚拟比赛 → 水平评估** 的闭环。

### 2.2 用户特征
- 单人使用，计算机专业大二学生；
- 具备基础编程能力，主要使用 C++ 参赛；
- 界面需全中文。

### 2.3 运行环境
- Windows 10/11 桌面应用；
- 联网场景：同步题库、查看题面；
- 离线场景：浏览已缓存题库、查看本地记录/笔记/模板、查看统计（不包含同步与题面）。

### 2.4 需求优先级定义
- **P0**：核心闭环必需，v1.0 必须交付；
- **P1**：重要增强，v1.0 计划交付；
- **P2**：锦上添花，视进度决定。

## 4. 非功能需求（NFR）

| 编号 | 类别 | 需求 |
| ---- | ---- | ---- |
| NFR-1 | 性能 | 冷启动 ≤ 5s；题库列表翻页/筛选响应 ≤ 500ms；统计页渲染 ≤ 1s |
| NFR-2 | 可靠性 | CF 同步失败不影响本地数据；数据库异常自动备份提示；离线可用 |
| NFR-3 | 易用性 | 全中文界面；主要操作 ≤ 3 次点击；键盘可达（Tab/Enter） |
| NFR-4 | 安全 | 渲染进程不直接访问 Node API（contextIsolation）；题面窗口沙箱隔离（v1.7 独立窗口同样沙箱 + 白名单）；无任何账号与网络上传（数据不出本机） |
| NFR-5 | 可维护性 | 分层清晰（main/preload/renderer）；数据库访问集中到 repository 层；关键算法纯函数化可单测 |
| NFR-6 | 兼容性 | Windows 10/11；高分屏（DPI）适配 |
| NFR-7 | 数据一致性 | 记录/笔记/模板修改即时落库；ID 唯一且稳定 |

> **NFR-1 的性能量化补充（v1.14.1）**：NFR-1 只给了「冷启动 ≤ 5s / 列表 ≤ 500ms / 统计 ≤ 1s」的口径，未覆盖
> **3 万题量级**下「首屏一次性取全库」这类真实压力场景（v1.14.0 因此出现 9 秒级卡顿）。v1.14.1 以
> **FR-34**（见 §6 末尾）为该类场景补上可验收的数字与实现约束：题库 3 万题时首页首屏取数 **≤ 1s**，
> 且**任何同步 SQL 都不得把主进程阻塞到秒级**。

## 5. 验收标准（概要，详见 04）
1. 全部 P0 功能需求可演示、可操作；
2. 04 测试规范中「手动验收清单」全部勾选通过；
3. 核心算法（水平评估、罚时计算、组卷）通过单元测试；
4. 应用在断网状态下仍可浏览已缓存题库与全部本地功能（题面除外）。

### FR-34 性能：大数据量下首页与启动不得阻塞（v1.14.1 新增，P0）
> 背景：v1.14.0 上线后用户反馈「首页跳转题库有明显卡顿」「启动速度明显变慢」。两个现象同一根因：
> 首页推荐习题要**题库全集**，原实现用分页 API 翻全量，真实库实测 **9072 ms**，而 better-sqlite3 是**同步** API
> 且跑在主进程 → 整个应用连同所有 IPC、页面跳转一起被堵住。完整复盘见 docs/08 §20。

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| FR-34.1 | 精简列全量取数 | 题库 **3 万题量级**（真实库 31764 题）下，首页推荐取全库**必须**走 `ProblemsRepo.leanAll()`：单条精简 SQL（`id/contestId/index/name/rating/difficulty/solvedCount/totalSubmit/source/cfUrl/fetchedAt` + 标签 `GROUP_CONCAT`），**不得**再用 `list()` 分页翻全量（每页 200 条共 159 页、每行 3 个相关子查询：标签聚合 / `EXISTS` 已练习 / 最近状态） |
| FR-34.2 | 量化门槛 | 真实库实测：原分页翻全量 **9072 ms** → 精简列单条 SQL **83 ms**（**109 倍**）；`leanAll()` 含 3.17 万行映射 **171 ms**。验收：首页统计卡片可见 **≤ 1s**、`recommend:get` 首次 **≤ 200ms**（实测 33 ms） |
| FR-34.3 | 不得阻塞主进程 | better-sqlite3 为**同步** API 且在主进程执行，任何 ms 级以上的查询都会连坐所有 IPC 与页面跳转 → 新增/修改首屏查询必须**先量化耗时**再上线（`npm run verify:perf` 即为量化手段） |

### FR-35 首页推荐去重：同一场比赛 / 同名题不占满推荐位（v1.15 新增，P1）
> 背景：用户反馈首页「推荐习题 → 未练习」栏 8 条**全是同一道题**（题名都叫 "Treasure Hunt"，id 为 `1639:A`…`1639:H`）。

> 再叠上同一场比赛的多道同名题。完整复盘见 docs/08 §21、设计见 docs/03 §26。

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| FR-35.1 | 0 值视为「未采集」 | 未练习排序取 AC 数时必须经 `acOf(p)`：`p.solvedCount > 0 ? p.solvedCount : Number.MAX_SAFE_INTEGER`。**`solved_count = 0` 代表从未采集到 AC 数**（CF 实验场/gym 题与部分洛谷题，真实库共 **132** 道，其中 117 道 `rating` 也是 NULL），**不得**当成「最少人做」排在最前；真实值缺失时统一当作未知值排到最后 |
| FR-35.2 | 同一场比赛最多 2 条 | `diversify(items, limit, perContest = 2)`：按「来源 + 比赛」分组计数，同一组在最终切片里**最多 2 条**（`contestKey = ${source}:c${contestId}`；无 `contestId` 时退化为按题目 id 各自成组） |
| FR-35.3 | 同一题名最多 1 条 | 按「来源 + 题名」去重（`nameKey = ${source}:${name}`），同名题在切片里**最多出现 1 条** —— 直接消灭「8 条推荐全叫 Treasure Hunt」 |
| FR-35.4 | 不丢弃、只后移 | 超出上限的条目**按原顺序追加到队列后面**（`picked` + `overflow`），最后才 `slice(0, limit)`；因此**排序语义不变**，只是重复过多的条目被后移。`limit` 大于可用多样性时用溢出队列**回填**，绝不因为去重而少给条目 |
| FR-35.5 | 不改用户所选排序 | 只对**未练习段**做 `diversify(freshSorted, freshLimit)`；`recommendOrderFresh`（默认 `learning-node`）的排序口径、已练习段排序、`totals` 计数与各处筛选逻辑**均不变** |

### FR-37 标签筛选取并集并按命中标签数排序（v1.17 新增，P1）
> 背景：题库页标签筛选原为**交集**（题目必须**同时**带全部已选标签）。而技能树的知识点节点会挂**多个**标签
> （例如「贪心」节点同时挂 `greedy` 与 `贪心`），点节点等于勾选它关联的全部标签 —— 交集语义下经常一题都筛不出来，
> 与「点节点就是想看这个知识点的题」的预期相反。用户需求原文：「将标签筛选从取交集改为取并集，按照满足的标签数排列」。
> 目标：命中任一已选标签即入选；已选标签数 > 1 时，命中标签数多的题排在前面。设计见 docs/03 §28。

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| FR-37.1 | 并集语义 | 题库页标签筛选（`ProblemFilter.tags`）由**交集**改为**并集**：题目命中**任意一个**已选标签即入选，不再要求同时带全部已选标签。SQL 由 `GROUP BY pt.problem_id HAVING COUNT(DISTINCT t.id) = <已选标签数>` 改为子查询并集 `p.id IN (SELECT pt.problem_id FROM problem_tags pt JOIN tags t ON t.id = pt.tag_id WHERE t.name IN (@tag0, …))`。题库里不存在的标签仍被忽略，不会把列表清空 |
| FR-37.2 | 排序口径 | 已选标签数 > 1 时，第一排序键为「命中已选标签数」**降序**；命中数相同时**再**按用户所选排序方式（按难度 / 按题号 / 按 AC 数，含升序降序与「全部」视图的题源分组）排列 —— 用户所选排序不被丢弃，只是降级为第二键 |
| FR-37.3 | 命中数可见化 | 已选标签数 > 1 时：① 题目行标签区末尾显示角标 `命中 N/M`（class `.mini-tag.match`，琥珀色，`title` 为「命中 N / M 个已选标签」，M = 已选标签数、N = 该题命中数）；② 「已选」条在「全部清空」后显示提示「取并集 · 命中标签越多越靠前」（class `.match-hint`）。角标数据由前端 `matchCount(row)` 用 `row.tags` 与已选标签集合求交算出，**不由 SQL 回传** |
| FR-37.4 | 无标签时行为不变 | 未选任何标签时，SQL 与排序**与旧版逐字符一致**（`matchedTagsOrderPrefix()` 返回空串）：不生成命中数子查询、不显示角标与提示；只选 1 个标签时交集与并集等价、结果集不变，同样不显示角标与提示（此时排序无意义） |
| FR-37.5 | `tagsAny` 不受影响 | 题单「按知识点自动抽题」使用的 `ProblemFilter.tagsAny` **语义本来就是并集**，本版未改动其 SQL 分支，行为与旧版一致 |

**验收标准（FR-37）**：
1. 同时选中 `dp` + `graphs` 两个标签 → 列表列出带 `dp` **或** 带 `graphs` 的题（不是只列两者都带的题），分页 `total` 反映并集总数、翻页正常；
2. 命中两个标签的题排在命中一个标签的题之前（GUI 实测 `802:C` 排在 `801:B` 之前）；命中数相同时按用户所选排序（难度降序 / 题号序均正确）；`buildOrderSql()` 在有标签时以 `(SELECT COUNT(DISTINCT t.id)` 开头且含 `@tag0, @tag1`，无标签时与旧 SQL 完全一致；
3. 已选标签数 > 1 时题目行显示 `命中 2/2` / `命中 1/2` 角标、「已选」条显示「取并集 · 命中标签越多越靠前」；只选 1 个标签时两者都**不**显示；

### FR-38 中英文标签映射（v1.18 新增，P1）
> 背景：三源题库的标签语言不统一 —— Codeforces 题带英文标签（`greedy` / `dp` / `graphs`），洛谷与力扣题带中文标签
> （`贪心` / `动态规划` / `图论`）。同一概念两种拼写 → 同一个技能树节点（如「并查集」`tags: ['dsu', '并查集']`）在题库里
> **分裂成两套**；v1.17 的并集语义下，点节点勾选全部标签时，同一道题还会被算作**命中 2 个不同标签**（假象）。
> 真实库实测：`dsu + 并查集` 交集 **0** → 并集 **907**；`greedy + 贪心` 交集 **0** → 并集 **5752**。
> 目标：一个概念在库里**只有一个标签行**（canonical 取中文），写入即物化，查询与统计天然一致。设计见 docs/03 §29。

| 编号 | 需求 | 说明 |
| ---- | ---- | ---- |
| FR-38.1 | 别名归一到同一 canonical | 新增共享模块 `src/shared/tag-map.ts`：`TAG_ALIASES`（canonical → 别名数组，共 **53 个 canonical + 71 个别名 = 124 个名称**）、`canonicalTag(name)`（大小写与多余空白不敏感，未收录名原样返回）、`canonicalTags(names)`（canonical 化 + 去重 + 保序 + 过滤空串）、`TAG_ALIAS_TOTAL`。**canonical 取中文**（UI 全中文；洛谷 452 + 力扣 171 个中文标签远多于 CF 122 个 ASCII 标签） |
| FR-38.2 | 写入即物化 | `ProblemsRepo.upsertMany()` 写标签时走 `for (const tagName of canonicalTags(p.tags))` —— CF / 洛谷 / 力扣三条写入路径同时生效；同一题同时带 `greedy` 与 `贪心` 时 `canonicalTags` 去重，库里只留 `贪心` 一行。**不在查询期展开别名**：`COUNT(DISTINCT t.id)`（命中标签数排序）与 `tagUsage` 聚合在「一个概念只有一个标签行」时天然正确，查询期展开会把同一概念算成 2 个命中，排序与「命中 N/M」角标都会错 |
| FR-38.3 | 查询与统计同口径 | 查询侧 `buildWhere()`（`tags` 与 `tagsAny` 两分支）、`matchedTagsOrderPrefix()`、`idsForKnowledge()`、`tagUsage()` 全部先 `canonicalTags()` 再拼 `@tagN` / `@anyTagN` 绑定参数；统计侧 `src/main/services/skill.ts` 的 `nodeTagSet` 与记录侧 tags 都经 `canonicalTags(...).map(lower)`，技能报告输出 `tags: canonicalTags(n.tags)`（渲染层因此不用改）；分类侧 `src/shared/tag-categories.ts` 的 `categorizeTag()` 先 canonicalize 再归类，归不到再退回原始名归类（保留英文条目兼容） |
| FR-38.4 | 旧库自动迁移且幂等 | 新增并导出 `migrateProblemTagsToCanonical(db): number`，在 `src/main/db/index.ts` 的 `migrate()` **末尾**执行：找 `canonicalTag(name) !== name` 的别名行 → 事务内 `INSERT OR IGNORE` 确保 canonical 行存在 → 用 `INSERT OR IGNORE … SELECT` 把题目关联搬到 canonical → 删旧关联 → 删别名 tag 行；返回被合并的行数。**幂等**：第二次执行返回 **0**。先判等 `if (!target \| target.id === row.id) continue` 再删，否则会把自己的关联删掉 |
| FR-38.5 | 来源/赛事类标签不映射 | 未收录进 `TAG_ALIASES` 的标签**保留原样**：来源与赛事类（`Special Judge`、`ICPC`、`USACO`、`洛谷原创`、各省省选、年份）以及 `Ad-hoc`、`STL`、`Tarjan`、`K-D Tree` 等 —— 它们本来就不是「同一概念的不同拼写」，强行归一反而会污染筛选与统计 |

**验收标准（FR-38）**：
1. 题库标签筛选传 `greedy` 与传 `贪心` 得到**同样的题数**（真实库均为 **5752**）；传 `dsu` 与 `并查集` 同样等价（均为 **907**）；中英文混着传（`['greedy', '贪心']`）**不重复计数**；
2. 技能树「并查集」节点详情里**只有一个「并查集」标签**，不再出现 `dsu`；该节点的题数与「已练 / 已 AC」统计与按 `并查集` 手筛的结果一致；技能报告输出 `tags: ['并查集']` 而渲染层未改；

4. 来源/赛事类标签（`Special Judge` / `ICPC` / `洛谷原创` / 年份）迁移后仍在库里且**名称未被改写**；
5. 全量测试 **515/515（46 文件）**、`verify:gui` **112/112**、`verify:smoke` **33/33**、`tsc --noEmit -p tsconfig.node.json` 与 `vue-tsc --noEmit -p tsconfig.web.json` **0 错误**；**无新增 IPC 通道、无新增设置项、无新表、无新字段**。
