## 1. 数据库设计（SQLite）

数据库文件：`app.getPath('userData')/acm-trainer.db`。主进程启动时执行建表（幂等，`CREATE TABLE IF NOT EXISTS`）。

### 1.1 实体关系概览
```
problems ──< problem_tags >── tags
problems <── practice_records（练习记录）
problems <── notes（笔记，可选关联）
contests ──< contest_problems >── problems
contests ──< contest_submissions >── problems
rating_history（独立历史）
settings（KV）
templates（独立）
```

### 1.2 建表语句（DDL）
```sql
-- 知识点标签
CREATE TABLE IF NOT EXISTS tags (
  id   INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL UNIQUE          -- CF 标签名，如 'dp'
);

-- 题目（多数据源：cf / luogu / leetcode；v1.1 FR-8 / v1.9 FR-21）
CREATE TABLE IF NOT EXISTS problems (
  id           TEXT PRIMARY KEY,     -- '1741:A'(cf) / 'P1000'(luogu) / 'LC1'(leetcode)，前缀天然分区
  contest_id   INTEGER NOT NULL,     -- cf 竞赛号；luogu / leetcode 行固定 0
  "index"      TEXT NOT NULL,        -- cf 题号字母；luogu 行 = pid；leetcode 行 = titleSlug
  name         TEXT NOT NULL,
  rating       INTEGER,              -- CF 难度分（可能为空）；luogu / leetcode 行恒为 NULL
  difficulty   INTEGER,              -- 洛谷难度 0-7 / 力扣难度 1-3，仅对应来源行非空（v1.1 / v1.9）
  solved_count INTEGER NOT NULL DEFAULT 0,  -- cf: 全球 AC 数 / luogu: totalAccepted / leetcode: total_acs
  total_submit INTEGER NOT NULL DEFAULT 0,  -- luogu: totalSubmit / leetcode: total_submitted
  source       TEXT NOT NULL DEFAULT 'cf' CHECK (source IN ('cf','luogu','leetcode')),
  cf_url       TEXT NOT NULL,        -- 语义：来源题面 URL（cf / luogu / leetcode）
  fetched_at   TEXT NOT NULL,        -- 最近同步时间
  UNIQUE (contest_id, "index")
);
-- 迁移说明（v1.9 FR-21，代码见 src/main/db/index.ts）：
--   旧库（v1.1–v1.8）先 ALTER 补 source/difficulty/total_submit 三列，再检测 sqlite_master 中 problems 的建表 SQL
--   是否含 'leetcode'；不含则一次性重建：PRAGMA foreign_keys=OFF → 事务内 CREATE TABLE problems__v19(…新 CHECK)
--   → INSERT … SELECT 全量拷贝 → DROP TABLE problems → RENAME TO problems → 恢复 foreign_keys。
--   关闭外键是为避免 DROP TABLE 触发子表 ON DELETE CASCADE 清空 problem_tags / practice_records / 比赛关联；
--   重建后子表按表名 problems 继续引用，数据、索引与外键级联语义保留（集成测试锁定）。

CREATE TABLE IF NOT EXISTS problem_tags (
  problem_id TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  tag_id     INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (problem_id, tag_id)
);
CREATE INDEX IF NOT EXISTS idx_problem_tags_tag ON problem_tags(tag_id);

-- 练习记录
CREATE TABLE IF NOT EXISTS practice_records (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  problem_id       TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  status           TEXT    NOT NULL CHECK (status IN
                     ('AC','WA','TLE','RE','MLE','CE','SKIP','UNSOLVED')),
  duration_seconds INTEGER,          -- 本次练习耗时（秒）
  note             TEXT,             -- 备注
  is_mistake       INTEGER NOT NULL DEFAULT 0,   -- 是否标记错题
  created_at       TEXT    NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_records_problem ON practice_records(problem_id);
CREATE INDEX IF NOT EXISTS idx_records_created ON practice_records(created_at);

-- 笔记（错题本/题解）
CREATE TABLE IF NOT EXISTS notes (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  problem_id TEXT REFERENCES problems(id) ON DELETE SET NULL, -- 可选关联题目
  title      TEXT NOT NULL,
  content    TEXT NOT NULL DEFAULT '',  -- Markdown 原文
  tags       TEXT NOT NULL DEFAULT '',  -- 逗号分隔的自定义标签
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_notes_problem ON notes(problem_id);

-- 代码模板
CREATE TABLE IF NOT EXISTS templates (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  category    TEXT NOT NULL,           -- 分类：图论/DP/数论/数据结构/字符串/其他
  title       TEXT NOT NULL,
  language    TEXT NOT NULL DEFAULT 'C++',
  description TEXT NOT NULL DEFAULT '',
  code        TEXT NOT NULL DEFAULT '',
  created_at  TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- 虚拟比赛
CREATE TABLE IF NOT EXISTS contests (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  name             TEXT NOT NULL,
  duration_minutes INTEGER NOT NULL,
  status           TEXT NOT NULL DEFAULT 'pending'
                     CHECK (status IN ('pending','running','finished')),
  started_at       TEXT,
  finished_at      TEXT,
  created_at       TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE TABLE IF NOT EXISTS contest_problems (
  contest_id INTEGER NOT NULL REFERENCES contests(id) ON DELETE CASCADE,
  position   INTEGER NOT NULL,        -- 0=A, 1=B, ...
  problem_id TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  PRIMARY KEY (contest_id, position)
);

CREATE TABLE IF NOT EXISTS contest_submissions (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  contest_id      INTEGER NOT NULL REFERENCES contests(id) ON DELETE CASCADE,
  problem_id      TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  status          TEXT    NOT NULL,   -- AC/WA/TLE/RE/CE/MLE
  seconds_elapsed INTEGER NOT NULL,   -- 比赛开始后经过的秒数
  submitted_at    TEXT    NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_contest_sub ON contest_submissions(contest_id);

-- 水平评估历史
CREATE TABLE IF NOT EXISTS rating_history (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  rating     INTEGER NOT NULL,
  source     TEXT    NOT NULL,        -- 'practice' | 'contest' | 'manual'
  detail     TEXT,                    -- 例如比赛名
  created_at TEXT    NOT NULL DEFAULT (datetime('now','localtime'))
);

-- 题单（v1.10 FR-27）
CREATE TABLE IF NOT EXISTS problem_lists (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  name        TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  -- 来源：manual=手动勾选 / paste=粘贴识别 / generate=按知识点生成
  origin      TEXT NOT NULL DEFAULT 'manual',
  -- 关联比赛赛道（可选：lanqiao / gplt / icpc / noip / nowcoder）
  track_id    TEXT,
  created_at  TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at  TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- 题单条目（含 v1.10 FR-29 间隔复习状态）
CREATE TABLE IF NOT EXISTS problem_list_items (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  list_id        INTEGER NOT NULL REFERENCES problem_lists(id) ON DELETE CASCADE,
  problem_id     TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  position       INTEGER NOT NULL DEFAULT 0,
  done           INTEGER NOT NULL DEFAULT 0,
  done_at        TEXT,
  note           TEXT NOT NULL DEFAULT '',
  -- 复习：stage 0=未进入复习（未完成）/ 1..6 = 1/3/7/14/30/60 天阶梯
  review_stage   INTEGER NOT NULL DEFAULT 0,
  review_due     TEXT,
  review_last_at TEXT,
  review_ease    TEXT,
  UNIQUE (list_id, problem_id)

CREATE INDEX IF NOT EXISTS idx_list_items_list ON problem_list_items(list_id);
CREATE INDEX IF NOT EXISTS idx_list_items_due ON problem_list_items(review_due);

-- 训练计划（v1.10 FR-28）：日历排期式
CREATE TABLE IF NOT EXISTS training_plans (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  name           TEXT NOT NULL,
  list_id        INTEGER REFERENCES problem_lists(id) ON DELETE SET NULL,
  target_date    TEXT,
  daily_target   INTEGER NOT NULL DEFAULT 3,
  rating_min     INTEGER,
  rating_max     INTEGER,
  -- 优先知识点（技能树节点 id，JSON 数组）
  knowledge_ids  TEXT NOT NULL DEFAULT '[]',
  -- 每周固定休息日（0=周日 … 6=周六，JSON 数组）
  rest_weekdays  TEXT NOT NULL DEFAULT '[]',
  track_id       TEXT,
  created_at     TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  updated_at     TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE TABLE IF NOT EXISTS plan_tasks (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_id    INTEGER NOT NULL REFERENCES training_plans(id) ON DELETE CASCADE,
  problem_id TEXT    NOT NULL REFERENCES problems(id) ON DELETE CASCADE,
  due_date   TEXT    NOT NULL,
  status     TEXT    NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','done','skipped')),
  done_at    TEXT,
```

## 4. 外部对接设计

### 4.1 Codeforces API
- 端点：`GET https://codeforces.com/api/problemset.problems`
- 响应结构（官方）：`{ status:'OK', result: { problems: [{ contestId, index, name, type, rating?, tags[] }], problemStatistics: [{ contestId, index, solvedCount }] } }`
- 字段映射：
  - `problems.id = `${contestId}:${index}``，`cf_url = https://codeforces.com/problemset/problem/${contestId}/${index}`
  - 仅收录 `type === 'PROGRAMMING'` 的题目（过滤 CF 的"选择题"类）；
  - `solvedCount` 按 (contestId,index) 与 statistics 合并。
- 同步策略：
  - 全量拉取（一次请求约 2–4MB JSON）；
  - 事务内 upsert（按主键冲突更新 name/rating/tags/solvedCount）；
  - 删除：本地存在但 CF 已下架的题目保留（避免历史数据丢失），标记不强制；
  - 请求间隔 ≥ 2s；网络失败重试 1 次（指数退避 1s）；仍失败返回错误码 `CF_FETCH_FAILED`，本地缓存不受影响。
- 频率/礼貌：同步为手动触发 + 启动超过 24h 提示，不自动高频拉取。

### 4.2 内嵌题面（WebContentsView，v1.7 起废弃，由 §13.1 独立窗口取代）
- 主进程维护一个常驻的 `WebContentsView` 实例，挂载在主窗口右侧区域（可关闭/重开）；
- 打开：`view.webContents.loadURL(problem.cfUrl)`；
- 安全：
  - `webPreferences: { sandbox: true, contextIsolation: true, nodeIntegration: false }`；
  - `will-navigate` / `setWindowOpenHandler`：新窗口一律 `shell.openExternal`（系统浏览器）或拒绝；
  - 仅允许导航到 `https://codeforces.com/*` 与 `https://cdn.codeforces.com/*`（外部链接走系统浏览器）；
  - 禁止下载（`will-download` 拦截）。
- 窗口联动：主窗口 resize 时同步调整 view 尺寸与位置（右侧固定宽度 ~60%）。

## 5. 水平评估算法（v1，纯函数、可单测）

### 5.1 输入
- 练习记录（近 90 天，含 CF rating 的题目）；
- 已结束的虚拟比赛（近 90 天，最近 3 场）。

### 5.2 练习分 PracticeRating
```
设尝试集合 T = { (r_i, s_i) }，r_i 为题 rating（无 rating 的题目剔除），
   s_i = 1 若该题最近一次练习为 AC，否则 0（WA/其他视为未通过）。
正确率 acc = Σ s_i / |T|（|T| = 0 时练习分无效）
难度均值 avgR = Σ r_i / |T|
PracticeRating = clamp( round( avgR − (1 − acc) × 300 ), 800, 3500 )
```
> 直观含义：全部 AC ≈ 题目平均难度；正确率每低一截，估算分相应下调。

### 5.3 比赛分 ContestRating
```
对最近 3 场已结束比赛（不足 3 场取实际场数；0 场则比赛分无效）：
  solved = 该场 AC 的题目（有 rating 者）
  solvedAvg = mean(r_i)，若 solved 为空则该场无效
  penaltyMin = 总罚时秒数 / 60
  contest_i = clamp( round( solvedAvg − penaltyMin × 2 ), 800, 3500 )
ContestRating = mean(有效的 contest_i)
```

### 5.4 综合 Rating 与称号
```
若比赛分无效：final = PracticeRating
否则：final = round( 0.7 × PracticeRating + 0.3 × ContestRating )

称号映射（参考 CF 颜色区间）：
  < 1000         新手 Newbie（灰 #808080）
  1000 – 1199    入门 Pupil（绿 #008000）
  1200 – 1399    进阶 Specialist（青 #03a89e）
  1400 – 1599    省赛候选 Expert（蓝 #0000ff）
  1600 – 1899    区域赛候选 Candidate Master（紫 #aa00aa）
  1900 – 2199    区域赛选手 Master（橙 #ff8c00）
  ≥ 2200         顶尖选手 International Master+（红 #ff0000）
```
- 写入 `rating_history` 并展示分解项（练习分/比赛分/正确率/有效题数）与趋势折线图；
- 界面固定展示免责声明：仅为本地训练参考，不代表真实 CF 分值。

## 6. 虚拟比赛规则

### 6.1 组卷算法（纯函数）
1. 按条件（rating 区间、tags、排除已用题目）从题库取候选；
2. 按 rating 排序后，用**确定性洗牌 + 均匀抽取**：将候选按 rating 分成 count 个桶，每桶抽 1 题，保证难度覆盖均匀；
3. 候选不足时允许降级（放宽 rating 区间），仍不足则报错提示。

### 6.2 比赛流程
- `contests:create` 生成题序 A/B/C…；`contests:start` 记录 `started_at`；
- 提交：`contest:submit` 记录 `seconds_elapsed = now - started_at`；
- 每题罚时（ACM）：`penalty_seconds = acSeconds + wrongCount × 20 × 60`，其中 `wrongCount` = AC 前非 AC 提交次数；
- 结束：`contests:finish` 计算
  - 排名依据：`solvedCount` 降序，`totalPenaltySeconds` 升序（单人模式展示数值）；
  - 结果写入比赛记录并触发评分（写入 rating_history，source='contest'，detail=比赛名）。

## 18. 力扣数据源同步（v1.9 FR-21）

### 18.1 站点范围与网络
- 仅支持 **leetcode.cn（力扣中文站）**；`leetcode.com` 在本机网络实测超时，不实现；
- 抓取在**主进程**用 Electron `net.fetch`（Chromium 网络栈，自动走系统代理），统一带
  `User-Agent`（Windows Chrome 126）、`Referer: https://leetcode.cn/problemset/`、`Accept: application/json`；
- 两个接口均**非稳定公开 API**：单请求失败重试 1 次（间隔 1200ms），仍失败抛
  `LEETCODE_FETCH_FAILED`（中文提示：需要可访问的网络、代理需对应用生效），已入库数据不受影响。

### 18.2 接口一：全量算法题列表（REST）
- 端点：`GET https://leetcode.cn/api/problems/algorithms/` —— **一次拿到全量列表**（约 1.5MB JSON，3930 道算法题）；
- 用到的字段：`stat.frontend_question_id`（题号）、`stat.question__title`（英文标题）、`stat.question__title_slug`（slug）、
  `stat.total_acs` / `stat.total_submitted`（全球通过/提交数）、`difficulty.level`（难度 1/2/3）、`paid_only`（是否会员题）；
- 解析纯函数 `parseLeetcodeList(jsonText) → LeetcodeListItem[]`（`src/main/services/leetcode.ts`），结构异常抛 `LEETCODE_PARSE_FAILED`。

### 18.3 接口二：GraphQL 分页取中文标题与中文标签
- 端点：`POST https://leetcode.cn/graphql/`，body：
  `operationName: 'problemsetQuestionList'`、`variables: { categorySlug: 'algorithms', limit ≤ 100, skip, filters: {} }`，

## 19. 难度分布统计（v1.9 FR-22）

### 19.1 数据链路
- IPC `stats:difficulty`（无入参）→ `RecordsRepo.difficultyStats()` → 纯函数组装；
- SQL 聚合（`src/main/db/repositories/records.ts`，一条语句完成分档与计数）：
```sql
SELECT p.source AS source,
       CASE
         WHEN p.source = 'cf' THEN
           CASE WHEN p.rating IS NULL THEN 'na'
                WHEN p.rating < 800 THEN 'lt800'
                WHEN p.rating >= 3000 THEN 'ge3000'
                ELSE CAST(p.rating / 200 * 200 AS TEXT) END
         WHEN p.source IN ('luogu','leetcode') THEN
           CASE WHEN p.difficulty IS NULL THEN 'na' ELSE 'd' || p.difficulty END
         ELSE 'na'
       END AS bucket,
       COUNT(DISTINCT p.id) AS attempted,
       COUNT(DISTINCT CASE WHEN r.status = 'AC' THEN p.id END) AS ac
FROM practice_records r JOIN problems p ON p.id = r.problem_id
GROUP BY p.source, bucket
```
- 组装：`services/difficulty-stats.ts > buildDifficultyStats(rows)` → `{ cf, luogu, leetcode }`，每项
  `DifficultySourceStats = { source, attempted, ac, buckets[] }`，档位
  `DifficultyBucket = { key, label, attempted, ac, acRate, share }`
  （`acRate = ac / attempted`，`attempted = 0` 时为 `null`；`share = attempted / 该题源已练题数 × 100`）。

### 19.2 分档口径与零填充
- **CF**：rating 每 **200** 一档 —— `<800`、`800–999`、`1000–1199` … `2800–2999`、`3000+`；`rating IS NULL` 单列「未标难度」（键 `na`）；
- **洛谷**：难度 `0–7`（`0 · 暂无评定` … `7 · NOI/NOI+/CTSC`）；**力扣**：`1–3`（简单 / 中等 / 困难）；
- **零填充规则**：洛谷 8 档与力扣 3 档**始终展示**（便于看分布，`canonicalKeys`）；
  CF 没有固定档全集，只补齐「有数据的最小档 ~ 最大档」之间的空档，**不虚构两端**；
  「未标难度」档有数据才出现且**排在最后**。

### 19.3 UI（pages/StatsPage.vue）
- 统计页新增板块「**难度分布（按题源）**」：题源切换按钮（`Codeforces（rating 分段）` / `洛谷（难度 0–7）` / `力扣（简单/中等/困难）`）
  + ECharts 柱状图（**已练题目 / 已 AC 双系列**）+ 表格（难度档 / 已练题目 / 已 AC / AC 率 / 占比 + **合计行**，0 值行置灰）；
- 进入页面（或数据加载完成）后**自动定位到已练题数最多的题源**；该题源 `attempted === 0` 时显示空态提示（不渲染图表）。

## 20. 题库排序规则（v1.9.1 FR-25）

### 20.1 缺陷背景（用户反馈：按难度/按题号排序异常）
三个根因叠加，均源于「三题源共用一套排序表达式」：
1. **按难度完全无效**：原实现统一用 `p.rating` 排序，但洛谷/力扣行的 `rating` **恒为 NULL**（难度存在 `difficulty` 列：洛谷 0–7、力扣 1–3），
   `ORDER BY p.rating` 对这两列全等 → 洛谷/力扣视图里「按难度」表现为**点了没反应**；
2. **按题号不是数字序**：「全部」视图里洛谷行按 `p.id`（TEXT）排序 → `P10000` 排在 `P1001` **之前**（字符串序错误）；
   力扣非数字题号（`LCR 001` / `面试题 xx` / `cnHoX6`）被 `CAST` 成 0，与数字题号混在一起；
3. **空难度位置会翻转**：降序时空值标记 `p.rating IS NULL` 也跟着 `DESC` → 未标难度/未定级的题跑到列表**最前**。

### 20.2 `buildOrderSql(filter)` 设计（`src/main/db/repositories/problems.ts`，新增并导出）
以「难度键 / 题号键**按题源取列**」+「空值标记恒 ASC」为核心，返回**完整 ORDER BY 子句**（含方向），由 `list()` 直接拼进 SQL：

| 键 | Codeforces | 洛谷 | 力扣 |
| -- | ---------- | ---- | ---- |
| 难度（空值标记） | `p.rating IS NULL` | `p.difficulty IS NULL` | `p.difficulty IS NULL` |
| 难度（取值） | `p.rating` | `p.difficulty`（0–7） | `p.difficulty`（1–3） |
| 题号（一级） | `p.contest_id` | `CAST(substr(p.id, 2) AS INTEGER)` | `CASE WHEN p.id GLOB 'LC[0-9]*' THEN 0 ELSE 1 END` |
| 题号（二级） | `p."index"` | — | `CAST(substr(p.id, 3) AS INTEGER)` |

- 「全部」视图：三源量纲不同，**不横向比较** → 先按题源分组（`CASE p.source WHEN 'cf' THEN 0 WHEN 'luogu' THEN 1 ELSE 2 END`，即 **CF → 洛谷 → 力扣**），
  组内再按该源口径排序（难度/题号各有一组 `CASE p.source …` 表达式）；
- **空值恒末位**：空值标记恒用 `ASC`（`false < true`），其余键用 `filter.sortDir` → 未标难度/未定级的题在升序与降序下**都在最后**；
- 每项排序键都是**一个完整表达式**（数组元素），最后 `.join(', ')` —— 顺带修掉原 `ID_EXPR` 用逗号拼接表达式、
  `CAST(substr(p.id, 2) AS INTEGER)` 被按逗号切碎导致 `near "ASC": syntax error` 的 SQL 缺陷；
- `sortBy === 'solvedCount'` 无空值概念，直接 `p.solved_count <dir>, p.id <dir>`。

### 20.3 生成结果示例（SQL 片段）
```sql
-- 单源「按难度」降序（洛谷）
ORDER BY p.difficulty IS NULL ASC, p.difficulty DESC, p.id DESC

-- 单源「按难度」降序（Codeforces）
ORDER BY p.rating IS NULL ASC, p.rating DESC, p.id DESC

-- 洛谷「按题号」升序（数字序：P10000 在 P1001 之后）
ORDER BY CAST(substr(p.id, 2) AS INTEGER) ASC, p.id ASC

-- 力扣「按题号」升序（数字题号在前，再按数字序）
ORDER BY CASE WHEN p.id GLOB 'LC[0-9]*' THEN 0 ELSE 1 END ASC,
         CAST(substr(p.id, 3) AS INTEGER) ASC, p.id ASC

-- 「全部」视图「按难度」降序（先题源分组，组内按该源难度列）
ORDER BY CASE p.source WHEN 'cf' THEN 0 WHEN 'luogu' THEN 1 ELSE 2 END ASC,
         CASE p.source WHEN 'cf' THEN p.rating IS NULL WHEN 'luogu' THEN p.difficulty IS NULL ELSE p.difficulty IS NULL END ASC,
         CASE p.source WHEN 'cf' THEN p.rating ELSE p.difficulty END DESC,
         p.id DESC
```

### 20.4 交互默认值（store + 页面）
- `stores/problems.ts` 新增 **`setSortBy(sortBy)`**：`setFilter({ sortBy, sortDir: sortBy === 'id' ? 'asc' : 'desc' })`
  —— **按题号 → 升序**，**按难度 / 按 AC 数 → 降序**（避免「选了什么都没变」的困惑）；
- `pages/ProblemsPage.vue` 排序下拉改为 `onSortBy()` 调用 `store.setSortBy()`（下拉选项仍为 按难度 / 按题号 / 按 AC 数，「↑ 升序 / ↓ 降序」按钮切换 `sortDir`）；
- **切换数据源时清空难度筛选**（`setSource()`）：洛谷 0–7 与力扣 1–3 量纲不同，避免「切过去变空列表」；
- 回归：`tests/integration/problems-sort.test.ts`（10 例）、`tests/renderer/problems-leetcode-source.test.ts`（+3 例）、`tools/gui-verify.cjs`（4 项断言：力扣题号升序 / 方向切换降序 / 力扣按难度 / 洛谷按难度）。

## 21. 题单与训练计划数据模型（v1.10 FR-27 / FR-28）

### 21.1 题单数据模型
- 表结构见 §1.2（`problem_lists` + `problem_list_items`）；两表通过 `problem_list_items.list_id` 级联删除，条目再通过 `problem_id` 级联到 `problems`；
- **`UNIQUE(list_id, problem_id)`** 是「同题不重复加入」的唯一权威来源：仓库层加入前先 `SELECT 1 … WHERE list_id=? AND problem_id=?`，
  已存在则跳过（`addProblems` 返回 `{ added, skipped }`），重复粘贴/重复勾选都幂等；
- 条目 `position` = `COALESCE(MAX(position), -1) + 1`（追加到末尾），移除条目只删该行、不影响其他条目次序；
- 仓库层：`src/main/db/repositories/lists.ts`（`ListsRepo`）。列表查询用**相关子查询**同时算出四个计数，
  供左侧题单列表直接渲染，避免前端 N+1：
  - `total` = 条目总数、`doneCount` = `done = 1` 数；
  - `reviewCount` = `review_stage > 0` 数（已进入复习）；
  - `dueCount` = `review_due <= 今天` 且 `review_stage > 0` 数（**待复习数**，逾期也算）。
- **派生字段与行映射**：`ListsRepo.detail` 不直接返回原始 SQL 行，而是把 `problem_id` 交给
  **`ProblemsRepo.byIds()`** 取完整题目对象（已完成行映射，含 `tags` 等派生字段）。
  这是 v1.10 的**缺陷修复点 1**：早期实现直接返回原始行，题目对象缺少 `tags`，
  页面 `tags.slice()` 抛错导致**题单详情页整页空白**（与 v1.8.4 水平评估页空白同一类问题）。

### 21.2 题单的三种题目来源
1. **从题库勾选**（`origin = 'manual'`）：题库页新增首列复选框（表头复选框 = 「勾选本页全部」）+ 工具条
   「已勾选 N 题 → 选择题单 / 新建题单 → 加入题单」；加入时把勾选的 id 数组**转成纯数组**再 `invoke`（见下文缺陷修复点 2）。
2. **粘贴题号文本识别**（`origin = 'paste'`）：纯函数 `parseCandidatesFromText(text)`（`src/main/services/problem-list.ts`）做**纯格式识别**，
   只产出 `RawCandidate { source, id }`，**是否存在于题库由调用方校验**：
   | 题源 | 可识别形式 | 归一化结果 |
   | ---- | ---- | ---- |
   | Codeforces | `1741A` / `1741:A` / `CF 1741 A` / `codeforces.com/.../problem/1741/A` | `1741:A` |
   | 洛谷 | `P3374` / `洛谷 P1000` / `luogu.com.cn/problem/P3374` | `P3374` |
   | 力扣 | `LC1` / `LC 146` / `leetcode.cn/problems/<slug>/` | `LC<题号>`（**链接按 slug 反查** `index = titleSlug` 得到 id） |
   - `resolveCandidates(repo, candidates)` 返回 `{ matchedIds, missing }`：命中项按题库顺序去重，
     **未命中项回显**（`missing` 截断为**最多 50 条**）—— 不静默丢题。
3. **按知识点 + 难度一键生成**（`origin = 'generate'`）：`pickProblemsForList(repo, opts)`：
   - 先按 `tagsAny = knowledgeTags`（**并集**）+ 数据源 + `rating` 区间 + `excludePracticed` 在 SQL 层取候选（`pageSize: 500`、按难度升序）；
   - 洛谷/力扣的 `difficulty` 区间**在内存里二次过滤**（CF 行用 `rating` 过滤，不受难度区间影响，避免两个条件互相干扰）；
   - **难度分层轮转**：把候选按难度键分桶 —— CF 为 `cf:<floor(rating/200)*200>`、其他源为 `<source>:d<difficulty>`、无难度为 `<source>:na`；
     对桶键排序后**逐轮各取一题**（round-robin），直到凑够 `count`。这样整份题单**不会挤在同一难度**。

### 21.3 训练计划数据模型与排期纯函数
- 表结构见 §1.2（`training_plans` + `plan_tasks` + `plan_busy_days`）；
  `training_plans.list_id` 用 **`ON DELETE SET NULL`**（题单被删不连坐计划，退化为「显式题目列表/自动抽题」模式），
  `plan_tasks.plan_id` 与 `plan_busy_days.plan_id` 用 **`ON DELETE CASCADE`**；
- `knowledge_ids` 与 `rest_weekdays` 以 **JSON 数组字符串**存储（SQLite 无数组类型）；`rest_weekdays` 口径 **0=周日 … 6=周六**（`Date.getDay()`）；
- 仓库层：`src/main/db/repositories/plans.ts`（`PlansRepo`），同样通过 `ProblemsRepo.byIds()` 做行映射；
- 纯函数：`src/main/services/training-plan.ts`
  | 函数 | 签名要点 | 语义 |
  | ---- | ---- | ---- |
  | `isWorkingDay(date, {restWeekdays, busyDates})` | `date = 'YYYY-MM-DD'` | 非每周休息日、非没空日才算可用日 |
  | `nextWorkingDay(date, opts, maxDays = 3650)` | 含传入日期本身 | 向后找第一个可用日（`maxDays` 防御死循环） |
  | `scheduleProblems(problemIds, opts)` | `opts: {dailyTarget, restWeekdays?, busyDates?, targetDate?, startDate?, maxDays?}` | 返回 `{ tasks: [{problemId, dueDate}], overflow, lastDate }` |
  | `shiftTasks(tasks, fromDate, shiftDays = 1, opts)` | — | 从 `fromDate`（含）起的**未完成**任务整体 +`shiftDays`，并再吸附到下一个可用日 |
  | `planStats(tasks)` | — | `{ total, done, pending }` |
- **排期算法**（`scheduleProblems`）：`dailyTarget = max(1, floor(dailyTarget || 1))`；`day = nextWorkingDay(startDate ?? 今天)`；
  循环「若 `targetDate` 且 `day > targetDate` → `overflow += 剩余题数` 并 **break**；不可用日 → `day += 1` 继续；
  否则把接下来 `dailyTarget` 道题挂到 `day`，`day = nextWorkingDay(day + 1)`」；
  - 关键取舍：**超出目标日期的题量只计入 `overflow`，绝不硬塞进最后一天、也不静默丢弃**；
  - `guard < maxDays` 兜底，`maxDays` 默认 3650；
- **顺延**（`shiftTasks`）：只动 `status === 'pending'` 且 `dueDate >= fromDate` 的任务 ——
  **已完成（done）的任务不动**，因此「总题量不变、完成时间整体推迟」；`skipped` 同样不动；
- **重新排期**（`plans:reschedule`）：按新参数重新 `scheduleProblems`，与顺延互不替代。

## 22. 间隔复习算法（v1.10 FR-29）

### 22.1 阶梯与档位
`REVIEW_INTERVALS = [1, 3, 7, 14, 30, 60]`（天，`src/shared/types.ts`），对应 `review_stage` 1..6；
`review_stage = 0` 表示**尚未进入复习**（题单条目未完成）。`intervalForStage(stage)` 越界时取最后一档（封顶第 6 档 = 60 天）。

### 22.2 `nextReview(stage, ease, today)` 规则
| 输入 `stage` | 输入 `ease` | 输出 `stage'` | 输出 `due` |
| ---- | ---- | ---- | ---- |
| 0（首次完成） | `null`（无反馈） | **1** | `today + intervalForStage(1) = today + 1` |
| ≥1 | `hard`（困难） | `max(1, stage − 1)` —— **退一档，最低 1 档** | `today + intervalForStage(stage')` |
| ≥1 | `ok`（一般） | `min(6, stage + 1)` —— **进一档** | `today + intervalForStage(stage')` |
| ≥1 | `easy`（轻松） | `min(6, stage + 2)` —— **跳一档（+2），封顶 6** | `today + intervalForStage(stage')` |

- 日期一律用**本地** `'YYYY-MM-DD'`：`localDate(d = new Date())` 手工拼 `getFullYear/getMonth/getDate`，
  **不用 `toISOString()`**（后者是 UTC，会跨日偏移）；`addDays` 用 `Date.setDate` 做本地加减（跨月/跨年安全）；
  `diffDays(a, b) = round((b − a) / 86400000)`；
- 反馈语义（与界面一一对应）：**困难 → 退档重来 / 一般 → 正常推进 / 轻松 → 加速推进**。

### 22.3 到期判定与展示
- `isDue(item, today)`：`review_stage > 0 && review_due != null && diffDays(review_due, today) >= 0` ——
  即 **`review_due ≤ 今天`**，**逾期同样算到期**；未进入复习的条目**不算**到期；
- `isMastered(item)`：`review_stage >= REVIEW_INTERVALS.length`（已走完 6 档）；
- `reviewLabel(item)`：`stage ≤ 0` → `未开始`；已走完阶梯 → `第 N/6 档 · 已巩固`；
  否则 → `第 N/6 档 · 下次 <review_due>`（实测文案：`第 1/6 档 · 下次 2026-10-10`）；
- `lists:dueReviews` 跨**全部题单**汇总 `review_due ≤ 今天` 的条目（JOIN `problem_lists` 取题单名），
  每条附题号/题目/难度/档位/到期日，供「今日复习」Tab 渲染困难/一般/轻松/题面四个按钮；无到期条目时返回空数组、页面显示空态文案。

### 22.4 与题单完成状态的耦合（幂等）
- `lists:setDone(done = true)`：
  - 若 `review_stage = 0`（首次完成）→ `done = 1, done_at = 今天` 并**自动进入第 1 档**（`nextReview(0, null)` → stage 1、`review_due = 明天`）；
  - 若 `review_stage > 0`（已进入复习）→ **只更新 `done`/`done_at`，不动 `review_stage` 与 `review_due`**（重复勾选不清空复习排期）；
- `lists:setDone(done = false)`：**只清完成状态**（`done = 0, done_at = NULL`），
  `review_stage` / `review_due` / `review_ease` **全部保留** —— 「取消勾选不丢做题成果」；
- `lists:review(problemId, ease)`：按 §22.2 计算新档位与下次日期，写 `review_last_at = 今天`、`review_ease = ease`。
- 回归：`tests/unit/review.test.ts`（10 例）覆盖阶梯、退档下限、跳档上限、到期/逾期判定与文案。

### 24.2 `buildRecommendation` 数据流

### 24.3 遗忘曲线（已练习默认排序）
| 量 | 公式 / 规则 | 说明 |
| ---- | ---- | ---- |
| 期望间隔 | `interval = acCount > 0 ? 1 + 2 × (acCount - 1) : 0.5` | AC 越多，期望间隔越长（AC 1 次 = 1 天，2 次 = 3 天，3 次 = 5 天…）；未 AC 过按 0.5 天 |
| 记忆强度 | `memoryStrength = 1 / (1 + daysSince / (interval / 2))` | `daysSince` = 距最后一次练习的天数；当天刚练 → 1，越久越趋近 0 |
| 紧急度 | `forgettingUrgency = 1 - memoryStrength` | 降序排列；数值越大越该复习 |
| 阈值 | `forgettingUrgency >= 0.5` | 判为「该复习了」，条目高亮并置顶显示理由「遗忘曲线：已 N 天没碰，建议复习」 |

- 已练习段其余 4 种排序：**最近练过**（练习时间戳降序）/ **最久没碰**（练习时间戳升序）/ **正确率最低**（`AC 数 / 提交数` 升序）/ **难度从低到高**；
- 「最近练过 / 最久没碰」**必须用练习时间戳而非 `daysSince`** —— 同一天练的两道题 `daysSince` 都是 0，无法区分先后（v1.14.0 修复项之一）。

### 24.4 `mergeRecommendSettings` 优先级

- **缺陷**：早期实现末尾用 `.sort(dueReview, urgency)` 再排一次已练习段，把设置里选的「最近练过 / 最久没碰 / 正确率最低 / 难度」**全部覆盖**，实际永远按紧急度排序；

## 25. 性能设计：题库全量读取与缓存（v1.14.1 FR-34）

### 25.1 为什么不能用分页翻全量（实测数字）

v1.14.0 的首页推荐需要**题库全集**，实现是 `ProblemsRepo.list()` 逐页翻：每页 200 条、**共 159 页**，
而 `list()` 的每一行都带 **3 个相关子查询**：

| 子查询 | 作用 |
| ---- | ---- |
| 标签聚合 | `(SELECT GROUP_CONCAT(t.name, ',') FROM problem_tags pt JOIN tags t …)` |
| `EXISTS` 已练习 | 该题在 `practice_records` 中是否存在记录（`practiced` 列） |
| 最近状态 | 该题最近一次提交状态（`lastStatus` 列，驱动「已 AC / 未通过」徽章） |

真实库规模：**31764 题 / 94 条提交记录 / 113664 条题目标签关联 / 574 标签**。实测：

| 实现 | 耗时 | 说明 |
| ---- | ---- | ---- |
| `list()` 分页翻全量（159 页 × 200 行 × 3 子查询） | **9072 ms** | 每页一次 round-trip + 每行 3 次相关子查询 |
| 精简列全量**单条** SQL（无相关子查询） | **83 ms** | **109 倍**差距 |

**真正致命的是执行位置**：better-sqlite3 是**同步** API，全部跑在 Electron **主进程**。这不只是「首页慢 9 秒」——
主进程被占满的 9 秒里，**所有 IPC 调用、所有页面跳转、窗口事件都被排队**，于是用户感知到的是
「启动速度明显变慢」（首屏被推荐查询堵住）+「首页跳题库明显卡顿」（点击后要等主进程空闲）。

### 25.2 `leanAll()` / `candidates()` / `buildWhere()` 的职责划分

| 方法 | 位置 | 职责 | 关键点 |
| ---- | ---- | ---- | ---- |
| `leanAll(): ProblemRow[]` | `src/main/db/repositories/problems.ts` | 首页推荐取**全库**：单条精简 SQL，列 = `id/contestId/index/name/rating/difficulty/solvedCount/totalSubmit/source/cfUrl/fetchedAt` + 标签 `GROUP_CONCAT` 串 | 实测 **171 ms**（含 3.17 万行映射）；**不带**3 个相关子查询 → `practiced` 恒 `0`、`lastStatus` 恒 `null`，由调用方用 `practice_records` 自己聚合（正确且更快） |
| `candidates(filter, max = 5000): ProblemRow[]` | 同文件 | 虚拟比赛组卷取**全量候选**（不分页） | `max` 默认 5000 防止误用成「无上限导出」；结果仍走行映射（含 tags） |
| `private buildWhere(filter)` | 同文件 | 由筛选条件拼 `WHERE` 子句 + 参数 | **从 `list()` 抽出**，`list()` 与 `candidates()` 共用 → 两处筛选口径不会漂移 |
| `buildOrderSql(filter)` | 同文件（v1.9.1 引入） | 生成完整 `ORDER BY`（按题源取难度列、空值恒最后） | 形参类型收窄为 `Omit<ProblemFilter, 'page' \| 'pageSize'>` —— 排序不关心分页 |

`leanAll()` 的核心 SQL 形状（简化）：

```sql
SELECT p.id, p.contest_id AS contestId, p.idx AS index, p.name, p.rating, p.difficulty,
       p.solved_count AS solvedCount, p.total_submit AS totalSubmit,
       p.source, p.cf_url AS cfUrl, p.fetched_at AS fetchedAt,
       (SELECT GROUP_CONCAT(t.name, ',') FROM problem_tags pt
          JOIN tags t ON t.id = pt.tag_id WHERE pt.problem_id = p.id) AS tagCsv
FROM problems p
ORDER BY p.source, p.id;
```

> 标签用 `GROUP_CONCAT` 一次拼成 `"dp,greedy"` 再在 JS 侧 `split` —— 比「一行一标签」的笛卡尔结果省掉大量行对象分配。

### 25.3 三级缓存的键设计与失效策略

全部位于 `src/main/services/recommend-service.ts`：

| 缓存 | 缓存内容 | 键 | 失效 / 容量 |
| ---- | ---- | ---- | ---- |
| `leanCache` | `leanAll()` 的全库行（题库快照） | `libraryKey(repos)` = **题库题数 + 三个题源的最后同步时间** | `LEAN_TTL_MS = 5 * 60_000`（5 分钟）兜底；题量 > `FULL_SCAN_LIMIT = 60000` 时**退回分页**（防止内存失控） |
| `tagUsageCache` | 标签统计（`StatsTagUsage`） | 题库键 + **记录数** + 排序后的标签集 | 最多保留 **20** 组 |
| `resultCache` | 推荐结果（`RecommendResult`） | 题库键 + 记录数 + `stableInputKey(effective)` | 最多保留 **30** 组；`freshOrder === 'random'`（随机换一批）**不缓存** |

- **键即失效**：同步题库会改题数与同步时间 → 题库键变；新增提交会改记录数 → 后两个缓存的键跟着变；改设置会进 `stableInputKey` → 结果缓存键变。因此**不需要监听 DB 事件**，键一变旧条目自然不再命中（并随容量上限被淘汰）；
- **`libraryKey` 为什么不用「库文件 mtime」**：SQLite 的写入/回滚时机与文件 mtime 并不同步，反而会出现「数据变了但键没变」的假命中；
- **`stableInputKey(effective)`**：把 `filterTags` / `knowledgeIds` **排序后**再 `JSON.stringify` —— 否则用户点标签的顺序不同就会产生不同键，缓存形同虚设；
- **随机排序不缓存**：`freshOrder === 'random'` 的语义就是「每次换一批」，缓存会让按钮看起来失灵（`const cacheable = effective.freshOrder !== 'random'`）；
- **显式失效**：导出 `invalidateRecommendCache()`，供同步完成 / 数据导入后主动清空。

### 26.1 为什么 `solved_count = 0` 不能当排序键

`problems.solved_count` 的语义是「**从题源采集到的 AC 人数**」，不是「做过这道题的人数」。两个题源都有大量题目**从未采集到 AC 数**：

| 实测项（真实库，`%APPDATA%\acm-trainer\acm-trainer.db` 只读打开） | 数字 |
| ---- | ---- |
| 题库总题数 | **31764** |
| `solved_count = 0` 的题 | **132**（Codeforces **30** 道 = 实验场/gym 题；洛谷 **102** 道） |
| 其中 `rating` 同时为 NULL 的题 | **117** |
| 这 132 道题分布在几场比赛里 | **8** 场 |
| CF **1639** 这一场比赛的题数 / 题名去重后 | **11** 道 / **1** 个题名「Treasure Hunt」 |

未练习段的排序由 `byAc` 决定：

```ts
// 修复前
const byAc = (a, b) => a.p.solvedCount - b.p.solvedCount   // 0 被当成「最少人做」→ 排最前
  || ratingOf(a.p) - ratingOf(b.p)
  || a.p.id.localeCompare(b.p.id)
```

三个缺陷叠在一起：

1. **升序把 0 顶到最前**：`solvedCount = 0` 语义上是「未知」，数值上却是最小值，于是这 132 道题集体抢到未练习段的最前面；
2. **`rating` 破平局失效**：`ratingOf()` 对 `rating = null` 返回 `Number.MAX_SAFE_INTEGER`，而对 CF 1639 这 11 道题来说**全都是同一个值**，第一次比较恒为 0；
3. **`id` 破平局按字典序**：`1639:A` < `1639:B` < … < `1639:K` 恰好连号 → 11 条同名题紧挨在一起，`slice(0, 8)` 直接取前 8 条，于是「同一个题名出现 8 次」。

**复现路径**（不依赖 GUI，纯函数即可）：构造 11 条 `solvedCount = 0`、`rating = null`、`contestId = 1639`、`name = 'Treasure Hunt'`、id 为 `1639:A`…`1639:K` 的题目，加几条正常题，调 `buildRecommendation(..., { freshLimit: 8 })` —— 修复前 `fresh` 段的 8 条题名全是「Treasure Hunt」。这条路径已固化为 `tests/unit/recommend.test.ts` 的回归用例。

### 26.2 `acOf` 与 `diversify` 的算法

`src/main/services/recommend.ts`：

```ts
/** 0 = 未采集，视为未知值，排到最后（不再被当成最冷门） */
const acOf = (p: ProblemRow): number =>
  p.solvedCount > 0 ? p.solvedCount : Number.MAX_SAFE_INTEGER

const byAc = (a, b) =>
  acOf(a.p) - acOf(b.p) || ratingOf(a.p) - ratingOf(b.p) || a.p.id.localeCompare(b.p.id)
```

`acOf` 是**同文件内部辅助函数（不导出）**，替换 `byAc` 里裸用的 `solvedCount`，`weak-node` / `easier` / `harder` / `popular` / `learning-node` 五条排序路径**都经过它**（都走 `byAc` 兜底），所以一处修正即可全口径生效。

去重函数（**唯一新增导出**）：

```ts
export function diversify(
  items: RecommendedProblem[],
  limit: number,
  perContest = 2
): RecommendedProblem[] {
  const contestCount = new Map<string, number>()
  const nameSeen = new Set<string>()
  const picked: RecommendedProblem[] = []
  const overflow: RecommendedProblem[] = []
  for (const it of items) {
    const p = it.problem
    const contestKey = p.contestId == null ? `${p.source}:${p.id}` : `${p.source}:c${p.contestId}`
    const nameKey = `${p.source}:${p.name}`
    const used = contestCount.get(contestKey) ?? 0
    if (used < perContest && !nameSeen.has(nameKey)) {
      contestCount.set(contestKey, used + 1)
      nameSeen.add(nameKey)
      picked.push(it)
    } else {
      overflow.push(it)
    }
  }
  return [...picked, ...overflow].slice(0, Math.max(1, limit))
}
```

四个要点：

| 要点 | 设计 |
| ---- | ---- |
| **分组键** | 「来源 + 比赛」（`contestKey`）与「来源 + 题名」（`nameKey`）**都带 `source` 前缀** —— 否则洛谷 `P1001` 与 CF 里同名题会被误判为同一组 |
| **双阈值** | 比赛 **≤ `perContest`（默认 2）** 条、题名 **≤ 1** 条；两个条件任一不满足即进溢出队列 |
| **不丢弃** | `picked`（符合多样性）在前、`overflow`（超出上限）按**原相对顺序**跟在后面，最后统一 `slice(0, limit)`；`limit` 大于可用多样性时溢出条目**回填**，不会少给 |
| **不改排序语义** | 只重排「谁进前 N 条」，一旦回填就回到原排序；`freshOrder` 的语义（`learning-node` / `easier` / `harder` / `popular` / `random` / `weak-node`）完全不变 |

复杂度：一次遍历 + 两个哈希表，**O(n)** 时间、**O(n)** 空间；调用点只有一处 ——

```ts
const freshLimit = Math.max(1, Math.min(50, input.freshLimit ?? 8))
const fresh = diversify(freshSorted, freshLimit).map((r) => ({ … }))
```

（已练习段**不做**去重：题单里同一场比赛的多道题本来就该按遗忘曲线排序。）

### 26.3 STL 数据模型与「有 / 没有 `clear()`」对照

`src/shared/stl-reference.ts` 是**单一数据源**，应用内 STL 速查页与 `docs/10-STL参考.md` 由它生成：

```ts
export interface StlEntry {
  id: string
  category: StlCategory                      // 'sequence' | 'adapter' | 'associative' | 'misc' | 'algorithm' | 'tips'
  name: string                               // 名称（含头文件）
  summary: string                            // 一句话用途
  code: string                               // 关键 API / 用法（C++17）
  complexity?: string                         // 复杂度或量级
  pitfalls?: string                           // 常见坑 / 注意事项
  url?: string                                // 延伸阅读（cppreference 等）
}
```

- **条目 35 / 分类 6**：序列容器 4（`vector` / `deque` / `array` / `string`）、容器适配器 3（`stack` / `queue` / `priority_queue`）、关联容器 3（`set` / `map` / `unordered_*`）、其他常用 4（`pair/tuple` / `bitset` / 数值 / **`stl-init-clear`（新增）**）、算法库 10、技巧与坑 11；
- v1.15 的补全**全部落在既有条目的 `code` 与 `pitfalls` 字段里**（不新增 12 条条目，只在 12 个容器条目内补齐「初始化 / 增删改查 / 清空 / 释放」四段），因此条目总数只 +1（新增的对照条目）。

清空方式**天然分两派**，这是本轮最容易抄错的地方，故在数据里显式标注：

| 容器 / 适配器 | 有没有 `clear()` | 清空写法 | 释放内存 |
| ---- | ---- | ---- | ---- |
| `vector` / `deque` / `string` | 有 | `x.clear()`（`string` 也可 `x = ""`） | `vector<int>().swap(x)` 或 `x.shrink_to_fit()`（`clear()` **不缩容**） |
| `set` / `map` / `unordered_set` / `unordered_map` | 有 | `x.clear()`（按 key 删单个用 `erase(k)`） | 整表回收用 `Container().swap(x)`（节点逐个释放，慎用于大表） |
| `array<T, N>` | **没有** | `x.fill(T{})` 或 `x = {}`（聚合初始化） | 固定长度、无堆分配，无需释放 |
| `bitset<N>` | 没有 `clear()` | `x.reset()`（全清零）/ `x.reset(i)`（清一位） | 定长位图，无需释放 |
| `stack` / `queue` / `priority_queue` | **没有** | `x = {}`（C++11 起可直接赋值空对象）或 `stack<int>().swap(x)` | 后者同时**释放底层容器内存**；`x = {}` 只清空不保证缩容 |

`stl-init-clear` 条目把这套对照**一页打包**，并附 4 个坑：① 多测忘清空（全局容器跨 case 残留）；② 邻接表要**逐行** `clear()`（`g[i].clear()`，直接 `g.clear()` 会把 vector 数量也清掉）；③ `clear()` 只改 `size()`、**不缩容**（内存峰值仍在）；④ `getline` 前残留换行（`cin >> n` 之后要先 `getline` 吃掉 `\n`）。

### 26.4 `gen-stl-doc.cjs` 的分类解析缺陷与修法

`tools/gen-stl-doc.cjs` 把 TS 源文件里的 `STL_CATEGORIES` 解析出来，用于生成 `docs/10-STL参考.md` 的分类目录与分组标题。原实现用**全文正则**找「分类对象」：

而源文件里 `categoryMeta()` 有一个兜底返回值：

```ts
  STL_CATEGORIES.find((c) => c.key === key) ?? { key: 'misc', label: '其他', hint: '' }
```

### 27.1 为什么用共享 Pinia store，而不是事件总线 / 后端持久化

三条路都能做联动，代价差别很大：

| 方案 | 能否联动 | 代价 |
| ---- | ---- | ---- |
| 事件总线（`mitt` / 自定义事件） | 能 | 需要「谁先挂载谁订阅」的时序假设；页面卸载要记得解绑，漏一处就是泄漏 + 重复触发；`<RouterView />` 每次切页都重挂载，订阅/退订次数随切页次数线性增长 |
| 后端持久化（新设置项 / 新表） | 能 | 把「一次会话里的浏览偏好」升级成「用户设置」——必须出现在设置页、必须定默认值、老数据要迁移，还得占一个新键；而它本质**不是设置** |
| **共享 Pinia store（采用）** | 能 | **零新增**：`filter.source` 本来就是题库页的题源筛选状态 |

采用第三种的关键前提：`src/renderer/src/App.vue` 用的是 `<RouterView />` 且**没有 keep-alive** —— 切页时组件卸载、再挂载时从 store 读到的就是最新值，**不需要任何跨页同步机制**。store 是应用级单例，所以「首页读到的 source」和「题库页读到的 source」是同一个 ref。

```ts
// src/renderer/src/pages/DashboardPage.vue
const currentSource = computed<'all' | ProblemSource>(
  () => (problems.filter.source ?? 'all') as 'all' | ProblemSource
)
/** 切换题源：写回共享 store（题库页随之切换），再按新口径重取推荐与标签统计 */
function pickSource(source: 'all' | ProblemSource): void {
  if (currentSource.value === source) return
  problems.setSource(source)   // 写 store：题库页下次挂载时就是新题源
  void loadRecommend()          // 首页自己按新口径重取（不依赖 store 订阅）
  void loadTags()
}
```

注意 `pickSource()` **不依赖 `watch`**：写 store 之后**主动**再拉一次推荐与标签，避免「store 变了但 UI 没变」的时序问题；而且推荐与标签**两路都要带 `source`**，否则会出现「列表是洛谷的、计数还是全库的」这种自相矛盾。

### 27.2 数据流（首页 → store → IPC → repo → SQL）

```
[首页推荐区] 点 button[data-rec-source="luogu"]
   └─ pickSource('luogu')
        ├─ problems.setSource('luogu')                    // Pinia：filter.source = 'luogu'
        │     └─ void this.setFilter({ source, page: 1, ratingMin: null, ratingMax: null, difficulty: null })
        │           └─ problems:list（题库页下次挂载即按新题源查询）
        ├─ loadRecommend() → invoke('recommend:get', { filterTags, source: 'luogu' })
        │     └─ src/main/ipc/problems.ts handler
        │           └─ recommendProblems(repos, input)
        │                 ├─ mergeRecommendSettings()：source 归一化（cf/luogu/leetcode，其余 → all）
        │                 ├─ resultCache key = `${libraryKey}|${records.length}|${stableInputKey(effective)}`（含 source）
        │                 └─ buildRecommendation()：只保留命中该题源的题

                    └─ repos.problems.tagUsage(tags, 'luogu')

```

反向（题库页 → 首页）：`ProblemsPage.vue` 的题源按钮直接调 `store.setSource(...)`；首页下次挂载时 `currentSource` 读到的就是同一个值，`loadRecommend()` / `loadTags()` 都带上它 —— 于是「题库页选了洛谷，回首页推荐只剩洛谷」，且**不需要**任何事件通知。


`tagUsage()` 里题源条件与标签条件是 **AND** 关系，拼在同一段 `WHERE`：

```ts
const conds: string[] = []
const params: (string | number)[] = []
if (tagFilter && tagFilter.length > 0) {
  conds.push(`t.name IN (${tagFilter.map(() => '?').join(', ')})`)
  params.push(...tagFilter)
}

  params.push(source)
}
const where = conds.length > 0 ? `WHERE ${conds.join(' AND ')}` : ''
```

为什么不做成两段 SQL：题数 / 已练 / 已 AC 三个计数都在同一条 `GROUP BY t.id` 聚合里；题源条件一旦挪到外层 `HAVING` 或另起一段查询，就会出现「标签计数按题源收窄、但 `lastAt`（最近练习时间）仍来自全库」这类口径割裂。

### 27.4 缓存键为什么必须带 `source`

`practicedTags()` 有 5 分钟的 `tagUsageCache`，键原本只有「题库版本 + 记录数 + 标签集合」。题源进来后若不加进键：

1. 先在「全部」下算一遍标签统计 → 写入缓存；
2. 切到「洛谷」→ 键与上一次**完全相同** → **命中旧缓存**，标签面板仍显示全库题数，而推荐列表已经是洛谷的 → 用户看到「洛谷只有 12 题」却「推荐列表里还有 CF 题」。

所以 `source` 要和标签集合一起进键（标签数组排序后再 join，避免 `[a,b]` 与 `[b,a]` 各算一遍）：

```ts
const key = `${libraryKey(repos)}|${repos.records.count()}|${source}|${tags.slice().sort().join(',')}`
```

推荐结果同理：`resultCache` 的键是 `stableInputKey(effective)`，而 `effective` 里已含归一化后的 `source`，所以切题源天然不会互相污染（`freshOrder === 'random'` 依旧不缓存）。

### 27.5 空态与提示文案策略

题源收窄后最容易出现的困惑是「推荐怎么变少了 / 怎么空了」，所以文案遵循「**在哪一层收窄，就在那一层写明**」：

| 位置 | 「全部」时 | 收窄时 | 意图 |
| ---- | ---- | ---- | ---- |
| 题源行右侧 | 与题库页同步：当前推荐全部平台 | 与题库页同步：当前只推荐 洛谷 | 说明这是**同一个状态**，不是首页自己的私有开关 |
| 推荐面板标题 | （不显示） | 仅 洛谷（`[data-rec-scope]`） | 一眼看出当前列表口径 |
| 已练习标签面板标题 | 共 N 个知识点标签已练过 | 共 N 个知识点标签已练过（仅 洛谷） | 解释「为什么标签变少了」 |
| 未练习空态 | 题库中没有符合条件的未练习题目 | 洛谷中没有符合条件的未练习题目 | 把「空」归因到题源，而不是让人以为题库没题 |
| 按钮组悬停提示 | 与题库页共用同一个题源：在这里切换，题库页也会切到同一平台 | 同左 | 鼠标停上去就知道会联动 |

### 28.1 失败案例：知识点挂多标签 + 交集语义 = 常常筛出 0 题

技能树的**一个知识点节点可以挂多个标签**（`src/shared/skill-tree.ts` 里每个 `KnowledgeNode` 都有 `tags: string[]`，如 `id: 'greedy', name: '贪心', layer: 1, tags: ['greedy', '贪心']`），而「点节点 = 勾选它关联的**全部**标签」是既有交互（FR-17、FR-31）。于是「贪心」这类节点会一次带上两个标签：`greedy` 与 `贪心`。

交集语义要求题目**同时带全部已选标签**：

| 用户操作 | 交集语义（v1.16.0 及更早） | 用户预期 |
| ---- | ---- | ---- |
| 点技能树「贪心」节点（勾选 `greedy` + `贪心`） | 只返回**同时**带 `greedy` 和 `贪心` 的题；题库里绝大多数题只带其中一个 → 常筛出 **0 题** | 「点这个知识点，就看这个知识点的题」——应当列出全部贪心题 |
| 手动勾 `dp` + `graphs` | 只返回同时带两标签的题（少数派），列表远少于两个标签各自的题数之和 | 想看「动态规划**或**图论」的题，用于交叉复习 |
| 深链/旧标签残留一个**题库里不存在**的标签 | `t.name IN (…)` 匹配不到这个标签，但 `HAVING COUNT(DISTINCT t.id) = <已选标签数>` 仍要求命中全部已选数 → 整个列表**直接空掉** | 不存在的标签应当被忽略，其余标签照常筛 |

三个现象是同一个根因：**「已选标签数」被当成「必须命中的标签数」写死在 `HAVING` 里**。多标签节点让「已选数 > 1」成为常态，而题目几乎不会同时带满两个同义标签（`greedy` / `贪心` 只是同一概念的中英文两种叫法），交集就把「同义标签一起勾」这种最常见的操作变成了「筛空」。

### 28.2 并集 SQL：为什么弃用 `GROUP BY + HAVING`

交集版的写法把「命中标签数必须**等于**已选标签数」表达为聚合：

```sql
-- 交集（v1.16.0 及更早，已弃用）
p.id IN (
  SELECT pt.problem_id FROM problem_tags pt
  JOIN tags t ON t.id = pt.tag_id
  WHERE t.name IN (@tag0, @tag1)
  GROUP BY pt.problem_id
  HAVING COUNT(DISTINCT t.id) = 2          -- 常数 = 已选标签数
)
```

并集版只需要「存在命中的标签」：

```sql
-- 并集（v1.17.0）
p.id IN (
  SELECT pt.problem_id FROM problem_tags pt
  JOIN tags t ON t.id = pt.tag_id
  WHERE t.name IN (@tag0, @tag1)           -- 命中任一即被选出
)
```

弃用 `GROUP BY + HAVING` 的四个理由：

1. **`HAVING` 的常数正是要被改掉的语义**。`= <已选标签数>` 写死的是「必须全中」；改成「至少中一个」后这个常数退化为 `>= 1`，而「至少一条关联行存在」用 `IN (子查询)` 表达更直接 —— 分组聚合在这里是做减法（先聚起每组、再筛）而不是必需。
2. **未知标签在交集下会把列表清空，在并集下自然被忽略**。`t.name IN (…)` 只匹配题库里真实存在的标签名，「选中标签数」却按用户提交的数组长度算，两者一旦不一致（标签改名、深链脏值、题源未同步到该标签），交集就成了「永远不成立的等式」；并集没有这个耦合，多余的 `@tagN` 只是匹配不到任何行。
3. **可组合性**：`p.id IN (子查询)` 与 `ratingMin` / `source` / 关键字等条件都是平级的 `AND`，优化器可以自由选择 `problem_tags` 上的索引；聚合版把 `GROUP BY` 夹在 `WHERE` 与 `ORDER BY` 之间，排序键若也要数一遍命中标签，同一个聚合就要算两次。
4. **与抽题路径同构**：题单「按知识点自动抽题」用的 `filter.tagsAny`（FR-37.5）本来就是 `IN` 子查询并集。改完之后 `buildWhere()` 里两条标签分支只差「按 `tags` 还是按 `tagsAny`」这一层参数来源，语义不再分叉。`tagsAny` 本版**未改动**。

### 28.3 `matchedTagsOrderPrefix` 与 `buildWhere()` 的绑定参数共享约束

排序要按「命中标签数」降序，等于让每行再数一遍命中的标签数。实现上不复用 SQL 里的聚合结果，而是**加一个相关子查询作为第一排序键**：

```ts
// src/main/db/repositories/problems.ts（新增私有函数）
function matchedTagsOrderPrefix(tags?: string[]): string {
  if (!tags || tags.length === 0) return ''            // 未选标签 → 空串，ORDER BY 与旧版逐字符一致
  const ph = tags.map((_, i) => `@tag${i}`).join(', ')
  return `(SELECT COUNT(DISTINCT t.id) FROM problem_tags pt JOIN tags t ON t.id = pt.tag_id
           WHERE pt.problem_id = p.id AND t.name IN (${ph})) DESC, `
}
```

`buildOrderSql(filter)` 把它取成 `prefix`，拼在**4 个 return 分支**的 ORDER BY 最前面（按 `solved_count` / 按 `rating` / 按 `id`、以及「全部」视图的题源分组分支）。命中数相同时前缀的比较结果为 0，排序自然落到用户所选的那个键上 —— 用户排序没有被替换，只是降级为**第二键**。

**关键约束：排序子查询里的 `@tagN` 不是它自己注册的。** 这些具名参数由 `buildWhere()` 在构造 `filter.tags` 条件时注册（`params.tag0`、`params.tag1`…），`matchedTagsOrderPrefix()` 只是**复用同名参数**。因此：

- 调用方**必须先调 `buildWhere()`、拿到带 `@tagN` 的 `params`，再拼 ORDER BY 并执行** —— `list()`（`buildWhere()` → `buildOrderSql()`）与 `candidates()` 都已经是这个顺序；
- 两者**不能拆开单独使用**：只调 `buildOrderSql()` 会得到带 `@tag0/@tag1` 的 SQL 却没有对应绑定值，执行时缺参数直接抛错（不是静默返回反序结果）；
- 若将来给标签条件换参数命名（如改成 `@t0`）或改成位置参数 `?`，**必须同步改两处**，否则排序键会在运行时炸；这也是把两个函数放在同一文件、注释里写明「必须先 buildWhere」的原因。

另一条不能省的点：`tags` 为空时 `matchedTagsOrderPrefix()` 必须返回**空串**而不是 `''` 之外的任何空白（空格、换行），否则「未选标签的 SQL 与旧版逐字符一致」这条护栏就失效了 —— 用例 ⑨ 正是用 `toBe('p.rating IS NULL ASC, p.rating DESC, p.id DESC')` 锁住这一点，以后谁在前缀里多加一个空格都会红。

### 28.4 命中数角标的数据来源：前端 `matchCount()`，不在 SQL 回传

`ProblemsPage.vue` 新增：

```ts
// 该题命中了多少个「已选标签」（未选标签时返回 0）
function matchCount(row: ProblemRow): number {
  if (selectedTags.value.length === 0) return 0
  const sel = new Set(selectedTags.value)
  return row.tags.filter((t) => sel.has(t)).length
}
```

不复用后端的排序结果、也不给 `ProblemRow` 加「命中数」字段，原因有三：

1. **它是展示层派生数据**。命中数完全由「已选标签集合」与「该题标签集合」决定，而 `row.tags` 已经在列表结果里返回 —— 回传一个新字段等于把同一个信息存两份，还要改 `ProblemRow` 类型、`problems:list` 出参与所有构造该类型的夹具；
2. **口径必须与前端口径同源**。角标的 M 用的是 `selectedTags.length`（用户眼前看到的那几个标签），不是后端 `HAVING` 里的常数；若后端也算一遍，两处对「已选」的理解稍有偏差（比如去重、trim）就会出现「角标说 2/2，SQL 却按 1 个标签算」的漂移；
3. **求交是 O(题目标签数)**，单行标签通常 3–6 个，3 万题的列表也只对**当前页**渲染的行调用，代价可忽略。

展示条件：`selectedTags.length > 1 && matchCount(row) > 0` —— 只选 1 个标签时命中数恒为 1，角标没有信息量；命中 0 个的题在并集语义下**根本不会出现在列表里**，`> 0` 只是防御性判断。角标文案 `命中 N/M`，`title` 为「命中 N / M 个已选标签」，class `.mini-tag.match`（琥珀色，与普通标签 `.mini-tag` 区分）。「已选」条在「全部清空」后加 `<span class="dim small match-hint">取并集 · 命中标签越多越靠前</span>`，同样只在已选标签数 > 1 时出现 —— 单标签时交集与并集等价、排序也没有额外键，写提示反而会让人以为排序被改了。
